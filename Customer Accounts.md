# Customer registration and login

Open `/Account/Register` or `/Account/Login`. Restart the application after updating; startup applies the additive CustomerAccounts migration. Existing customers and reservations are retained. Existing reservation-only customers have no password and cannot be claimed by public signup. Account recovery or linking for legacy customer records needs an administrator-assisted process; it is not included here.

New customers register a name, email, phone and password of 10–128 characters. Passwords use the ASP.NET Core password hasher. Signup always creates a Customer; staff/admin privileges are never accepted from public registration. Confirm email before login using a single-use verification link that expires after 24 hours. Only a hash of the random verification token is stored. Resending replaces the old link and has a one-minute cooldown. Five incorrect passwords cause a 15-minute lockout; account endpoints also limit requests per remote IP.

The existing IEmailSender SMTP configuration sends verification emails. Keep its password in local User Secrets. Accounts:PublicBaseUrl determines the confirmation link's HTTPS origin and defaults to https://localhost:7096. Configure this for a different host or port. The address does not come from the incoming Host header. If sending fails, the account remains unverified and the user can request another message at `/Account/VerifyEmail`. No token bypass is exposed in the interface or logs.

Login issues the existing application cookie with role Customer, numeric CustomerID/NameIdentifier, customer name, email and session version. Reservation ownership therefore uses the same customer key. Cookies require HTTPS and are HTTP-only; redirect targets must be local URLs. Sign-out is a POST with antiforgery validation. `/Access` redirects to the real login unless the optional development preview is explicitly enabled; preview access is disabled by default. Staff/admin account provisioning and profile editing remain separate integration work.

## Forgotten passwords

The sign-in page links to `/Account/ForgotPassword`. Verified customers can request a reset email through the configured sender. The request screen uses the same response for recognised and unrecognised addresses. Unverified accounts should confirm their email first; legacy reservation-only records cannot be converted through password recovery.

Reset links use separate, random, hashed tokens. They expire after 30 minutes, can be used once, and are replaced when a new reset email is requested. Requests have a one-minute per-account cooldown plus the account endpoint rate limit. The new password must match its confirmation and have 10–128 characters. `/Account/ResetPassword` disables caching and referrer disclosure. Completing a reset consumes the token, resets password lockout counters, and increments the session version. Older customer login cookies are rejected on their next request. The user must sign in again; reset does not automatically log them in. No password or reset token is displayed or logged.

Restart the website to apply the additive CustomerPasswordReset migration. The sender and Accounts:PublicBaseUrl settings described above also apply to reset links. The design follows the relevant principles in the [OWASP Forgot Password Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html).

Run `dotnet run --project tests/RROMS.Sprint2.Tests -- --integration` for the combined reservation and account checks. Tests create and delete a uniquely named temporary LocalDB database. Account email transport is fake, and endpoint tests disable SMTP. The test server uses an unused HTTPS port and is stopped before cleanup. Checks cover registration validation, confirmation, password lockout, antiforgery, cookie login/logout, redirect safety, reservation ownership and denial of staff access. No real emails or existing application records are used.
